## Chosen path

Use one GitHub-hosted Actions workflow and one branch-restricted GitHub Environment, `karturt-r2-staging`. GitHub documents Environment secrets and required reviewers as available for public repositories on Free, and jobs wait for environment protection rules before receiving environment secrets ([plan availability and protection behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)). The workflow is `workflow_dispatch` only. It accepts dispatches from `main` by `Satsetx4`, checks out the policy at the event's exact SHA, and checks out only a separately authorized full candidate SHA into a sibling `candidate/` directory for execution. The candidate is verified and its dependencies are installed and its database commands run from that directory, keeping the trusted policy checkout outside the candidate Git worktree. Both authorization passes use read-only GitHub token scopes; the protected job also needs those read scopes for its post-approval recheck, then uses an ephemeral GitHub-hosted runner.

The candidate must be the merged head of PR #103 into main. The authorizer compares the tested candidate with the immutable PR merge result: the candidate must be an ancestor of that result or have an identical Git tree. It also requires the PR merge result to be an ancestor of the exact main commit that dispatched the workflow. The latest exact-SHA Gate A run must pass Gate A local verification, Launch Safety independent PostgreSQL concurrency, and R2 disposable PostgreSQL 18 recovery. The recovery job uses only an ephemeral PostgreSQL 18 service with synthetic data and no Neon credentials. Its verified scope is rebuild, migration replay, and fixture reseed; it does not prove Neon PITR or production recovery. The authorizer binds the recovery comment's run ID and attempt to this exact Gate A run and requires the named recovery proof step to pass. Before any operation, the runner also requires the exact karturt-r2-staging Environment, a custom branch rule for main only, and exactly one required reviewer: repository owner Satsetx4. Additional users or teams are rejected because GitHub releases the job after any one listed reviewer approves. Self-review prevention must be off so the configured owner reviewer can approve the run. The reviewer approval happens on every run.

Every `preflight`, `migrate`, and `synthetic-fixture-create` operation requires a separate owner-authored issue #98 GO that binds the exact candidate SHA, canonical target, and operation. The GO must reference operation prerequisites; every prerequisite comment must be older than the GO and both the GO and its evidence comments must remain unedited. A later matching NO-GO supersedes the GO, and one comment containing both GO and NO-GO is rejected. After Environment approval, the trusted `main` policy helper validates the linked evidence and then reads the latest owner decision again as its last GitHub API request immediately before starting the database command. It starts the candidate command only after authorization passes, forwarding an operation-specific environment allowlist; the child process does not receive `GITHUB_TOKEN` or unrelated environment values. This also rejects reruns of the protected job. Evidence comments must link `RUN: <run-id>/1`; the runner verifies the actual main-branch workflow run (`path` as returned by GitHub's workflow-runs API) and its successful operation step. Candidate dependencies install with `npm ci --ignore-scripts` before any step receives database or fixture secrets. The workflow uses a distinct run name to detect GO reuse, serializes staging runs, pins actions to full commit SHAs, disables package caching, and does not persist checkout credentials. Preflight gets both DB URLs, migration gets only the migrator URL, and fixture creation gets only the runtime URL plus four synthetic account credential values. No credential is printed by the runner.

The GitHub decision check and PostgreSQL connection cannot be one atomic transaction. A NO-GO posted after the final check cannot revoke a command that has already started. The same-step recheck keeps that interval to the authorization call and immediate process launch; the owner must treat the operation as committed once that check passes and verify a stop/failure before issuing another GO.

## CLI modes and write boundary

For a staging environment, `npm run db:migrate` and `npm run db:migrate -- --plan` print the frozen target, checked-out SHA, and journal head without opening a database connection. `--preflight` opens actual `node-postgres` connections using both role-specific URLs and validates effective identities, PostgreSQL 18, active TLS with certificate-chain and direct-hostname verification, role attributes/grants, denied `TEMP`, and the pre-migration catalog. It performs no DDL or DML. Before that preflight can pass, the owner must establish an owner-owned, empty `drizzle` schema, direct migrator `USAGE` and `CREATE` on that schema, direct migrator `CREATE` on `public`, and direct migrator database `CREATE`; no grant options, role membership, database `TEMP`, or admin role attributes are allowed. Those owner changes are not performed by this workflow and require their own exact target and scope approval. The migration `--apply` step receives only the migrator URL. It requires the exact SHA, target, operation, run/attempt, fresh issue #98 GO, and separate PASS references for preflight and isolation/recovery.

The journal is checked against all 14 frozen tags `0000`–`0013`. `synthetic-fixture-create` is a separate operation using the runtime DML role. It creates the reviewed synthetic RT/year/accounts/household/resident/dues fixture in one transaction and accepts a retry only when supplied credentials match the stored hashes and the complete fixed fixture passes relational checks. A partial or unrelated fixture fails closed. This is trusted bootstrap DML, not an authenticated app-path or tenant authorization test; R3 must still verify app authorization independently.

Migration recovery is not an automatic rollback. Drizzle runs the pending migration statements and their journal inserts in one PostgreSQL transaction, and the source migration files contain no explicit transaction breaks or nontransactional index operations. PostgreSQL should roll back that transaction if one of those statements fails. Drizzle creates its schema and journal table before opening that transaction, and the runner also commits default-privilege and failure-cleanup ACL changes separately. A failed attempt can therefore leave the empty journal table and those ACL changes behind. The strict empty-catalog preflight then stops rather than automatically replaying. Post-migration privilege checks happen after the migration transaction commits, so a failure there cannot undo the schema. The source migrations include destructive schema refactors and do not define down migrations. After any failed attempt, preserve the database and logs, do not retry or reset it, and require owner-only catalog and migration-journal readback plus a separately approved recovery decision. The current migration process also cannot set its own role back to `NOLOGIN` or revoke owner-controlled database/schema grants. A successful migration event is not R2 PASS; keep R2 blocked until the owner completes and verifies those cleanup steps and runtime privileges.

## Owner GO comment format

For each future operation, first add immutable, owner-authored, public, non-secret evidence comments on issue #98. Then add a new owner GO comment that references those earlier comments, binds the full candidate SHA and exact target, and is itself left unedited. The GO is single-use; any failed or interrupted run requires a fresh GO and fresh supporting evidence where the operation changed relevant state. The authorizer checks comment IDs and edit timestamps, then confirms the referenced evidence predates the GO.

```text
R2_RUNNER_GO: GO
SHA: <full-candidate-sha>
TARGET: flat-cloud-57657711/br-sparkling-flower-azordm9k/ep-red-boat-azzqyf45/karturt_staging
OPERATION: authenticated-tls-role-preflight
ISOLATION_EVIDENCE_COMMENT: #98/<immutable-comment-id-with-staging-recovery-proof>
```

The referenced isolation comment must contain exact `R2_ISOLATION_RESULT: PASS`, `SYNTHETIC_ONLY: PASS`, `STAGING_DISPOSABLE_RECOVERY: PASS`, `RECOVERY_TARGET: postgresql-18-disposable`, `RECOVERY_OPERATION: rebuild-reseed-official-migrations-0000-0013`, the candidate `SHA`, and the canonical `TARGET`. It must also say `NEON_INSTANT_RESTORE: NOT_RUN` and `PRODUCTION_RECOVERY: NOT_PROVEN`, then link `RECOVERY_RUN: <exact Gate A run ID>/<attempt>`. The authorizer verifies that the linked run is the latest successful exact-head run for the current candidate PR and that its named PG18 recovery job and proof step succeeded; a comment by itself cannot satisfy the gate.

Use `OPERATION: official-migrations-0000-0013` with separate `PREFLIGHT_EVIDENCE_COMMENT` and `ISOLATION_EVIDENCE_COMMENT` references for migration. Use `OPERATION: synthetic-fixture-create` with separate `MIGRATION_EVIDENCE_COMMENT` and `ISOLATION_EVIDENCE_COMMENT` references for fixture creation. The same immutable staging-specific recovery evidence is required for every operation GO. It does not satisfy any separate production recovery gate.

Do not put credentials, connection strings, resident information, or raw catalog output in that comment. The original GO for the frozen SHA does not authorize a new SHA.
