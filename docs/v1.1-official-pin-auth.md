# KartuRT V1.1 — Official Username + PIN

## One-page design

### Mobile flow

1. Residents continue to enter house number + six-digit PIN.
2. Ketua RT and Bendahara enter username + six-digit PIN on the Pengurus login path.
3. If an official has not set or has forgotten the PIN, the same page offers a recovery form. It requires the username, current 16–128-character official recovery password, and a new PIN entered twice. Recovery does not log the user in.
4. System Admin continues at `/system/login` with the existing strong password and verified TOTP flow.

### MVP capabilities

- Authenticate only active `official` accounts with exactly one active, date-valid official assignment. Resolve role and RT from the database; never accept either from the browser.
- Use the existing Better Auth password hash in `app_accounts.pin_hash` for the six-digit official PIN. PINs are ASCII digits and leading zeroes are valid.
- Make each official PIN distinct across official accounts. Check existing hashes under a transaction-scoped advisory lock, including the empty-table case; sign-in also rejects any pre-existing duplicate so each affected official can replace it through private recovery. Fail closed for an ambiguous identifier, corrupt hash, or more than 500 hashes to compare.
- Preserve the current strong Better Auth credential as a recovery factor. Recovery updates only `pin_hash`, revokes that user’s sessions, clears applicable lockouts, and writes the existing `account.pin.recovered` audit event.

## Role and credential boundaries

| Account | Login | Recovery / second factor |
| --- | --- | --- |
| Resident | Existing house number + six-digit PIN | Existing resident flows unchanged |
| Ketua RT / Bendahara | Username + six-digit PIN | Current strong account password can set/recover PIN; account PIN reset revokes sessions; enabled TOTP remains required |
| System Admin | Existing 16–128-character password | Verified TOTP remains mandatory; PIN login is not accepted |

The official recovery password remains a Better Auth credential and is never replaced by PIN login or PIN recovery. Public email/password sign-in is blocked at the Better Auth catch-all route; resident and System Admin logins continue through their existing role-specific wrapper. The custom official endpoint is called only inside the role wrapper.

## Security and consistency

- Use Better Auth `hashPassword`/`verifyPassword`, ordinary Better Auth sessions/cookies, and the existing 8-hour session lifetime. No custom session token format or plaintext PIN storage is introduced.
- Lockout: five failed official login or recovery attempts lock the relevant account for 15 minutes. Existing database-backed IP rate limits remain in force. User-facing authentication errors are generic.
- PIN changes and recovery serialize uniqueness checks with a PostgreSQL transaction-scoped advisory lock, then lock official account rows in stable ID order. Account mutation, session revocation, and audit write occur in the same transaction.
- Before issuing a PIN-login session, re-check the username, PIN hash, lockout state, TOTP state, and active assignment while locking the account. The TOTP challenge records a short-lived hash fingerprint so changing the PIN during an open challenge prevents that challenge from issuing a session.
- Existing official TOTP factors are preserved and verified through Better Auth. System Admin still uses Better Auth’s original password + TOTP path.
- Credential material must not be written to logs, audit context, screenshots, issues, or Git. Tests create credentials at runtime and retain only pass/fail evidence.

## Data and migration impact

No schema or data migration is required. The feature reuses the existing hashed `app_accounts.pin_hash`, Better Auth `authAccount.password`, account lockout columns, `authSession`, verification storage, official assignment table, and audit writer. There is no migration-journal change.

Production official passwords and PIN hashes are not changed by deploying this code. After a separate V1.1 Production GO, each official can privately choose a PIN through the recovery form using their existing strong password. No bulk PIN reset or shared default PIN is part of this release.

## Rollout stages and rollback

1. **Preview:** deploy this branch only to the Vercel Preview target after verifying its database target is a disposable synthetic environment. Never use the Production alias or real resident data for smoke tests.
2. **Synthetic verification:** use synthetic Chairman, Treasurer, Resident, and System Admin identities. Verify official PIN login, resident compatibility, Admin password+TOTP, role/RT isolation, lockouts, PIN recovery/change, session revocation, audit redaction, and existing financial/account invariants.
3. **Owner review:** review the exact PR head and its exact-SHA CI results. This PR stays open and unmerged. The V1 GO for `f48b5850f3669148536f850e2c9f687d433f154a` does not authorize a different SHA or Production action.
4. **Future Production cutover:** requires a separate explicit GO bound to the final source SHA and Production target. After that GO only, owners can privately set/recover official PINs and complete the bounded owner smoke. No migration or account mutation is needed before GO.
5. **Rollback:** a code-only revert restores the prior login behavior because the strong official Better Auth credential remains intact. A rollback is a different Production source SHA and requires its own explicit GO. Existing official PIN hashes are not destructive to the prior password login path.

## Verification plan

- Unit, integration, constraints, authorization, and security-closure suites; lint, typecheck, schema drift checks, and production build.
- Focused tests for the two roles, leading-zero PINs, duplicate PIN rejection, wrong-role attempts, ambiguous identifiers, inactive assignments, lockout thresholds, self-recovery, account PIN change, strong-password preservation, session revocation, TOTP, and login/change race behavior.
- Run PostgreSQL concurrency and PostgreSQL 18 recovery checks only against local disposable databases. If unavailable, report them as unavailable rather than passing.
- Browser Preview checks at 360–420 px, tablet, and desktop only after the Preview target is confirmed synthetic/disposable. No Production Vercel, Neon, import, payment, or real-account operation is in scope.
