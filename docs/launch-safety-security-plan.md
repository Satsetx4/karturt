# Launch Safety Security Plan

**Status:** Security test plan only; Launch Safety security tests have not been executed or independently audited in this document.
**Source baseline:** `4890678b91c4c4e2c535f1149da60dbfcde32370` (`feat/launch-safety-single-rt` at plan authoring).
**Scope:** Minimum launch-critical security checks for the approved Single-RT operating mode. Cross-RT isolation and authorization remain required and are exercised using multiple RT fixtures.

## Test rules and verdicts

- Exercise actual Next route handlers and domain/database services. Mock-only authorization tests do not prove server-side access control.
- Use disposable local fixtures and independent database transactions/connections for concurrency tests. Do not mutate shared Neon financial data or production.
- For denied requests, assert both the HTTP/domain result and that protected rows, ledger rows, sessions, and audit rows did not change. Responses must not expose credentials, tokens, database details, internal IDs, or unrelated resident data.
- A test marked **Existing baseline test** is a source reference to rerun and review on the Launch Safety branch. It is not a claim that the Launch Safety branch has passed it.

Severity rules:

- **Critical:** unauthorized financial effect, cross-RT access, privilege escalation, broken financial idempotency/concurrency, or unauthorized privileged-account recovery. Any Critical result is a launch blocker.
- **High:** unauthorized sensitive data access, stale privileged access, working CSRF against a privileged or financial mutation, credential guessing without an effective limit, or broken session revocation. Any launch-relevant High result is a launch blocker.
- **Medium:** validation, rate-limit, or error-handling weakness that does not permit unauthorized access or financial mutation. Classify from the demonstrated effect.
- **Low:** safe, bounded behavior or usability-only failure with no security or data-integrity consequence.

## Principal and route coverage checklist

For S1-S16, cover each principal category against the route families that can affect it:

| Principal/attempt | Required route coverage | Expected result |
|---|---|---|
| Resident | Own and another resident's dues, payment request/history/cancel, direct credential-reset attempt | Own allowed operations succeed; other-owner access and privileged actions deny without disclosing foreign data. |
| Treasurer | Queue/detail/verify/reject, cash, payment history/reversal, Chairman and resident routes | Own same-RT payment work succeeds; non-Treasurer actions deny. |
| Chairman | Household lifecycle, fee/adjustment, waiver, report, Treasurer routes | Same-RT Chairman permissions succeed; Treasurer-only and foreign-RT operations deny. |
| System Admin | TOTP-gated system recovery, audit, and non-system routes | Access only with verified TOTP and permitted recovery scope; no financial/Treasurer privilege is inferred. |
| Anonymous | Representative GET and POST routes in every family | 401 and no protected response or mutation. |
| Inactive account / ended assignment | Reuse previously valid session on protected routes | 401/403 after the database state changes. |
| Other user / other RT | Alter target IDs and known public request codes | Safe denial/not-found; zero foreign data or state change. |
| Spoofed tenant / role | Add `rtUnitId`, `role`, and actor fields across query/body/header | Server uses session/database identity only; no scope or permission change. |
| Direct API | Invoke route handlers without UI restrictions | Same authorization as a real browser path; no mutation when denied. |

The route-level suite should exercise actual handlers with authenticated cookie/session state. Domain tests should then verify the corresponding service transaction and database invariant. Expected statuses are route-contract specific (401, 403, 404, 409, or 415); the invariant is that denied or conflicting requests produce no unauthorized financial, identity, session, factor, or audit change.
