# Launch Safety Security Plan

**Status:** Focused actual-cookie route/session remediation tests have run on this branch; this document is not a complete independent security audit.
**Source baseline:** `4890678b91c4c4e2c535f1149da60dbfcde32370` (`feat/launch-safety-single-rt` at plan authoring).
**Scope:** Minimum launch-critical security checks for the approved Single-RT operating mode. Cross-RT isolation and authorization remain required and are exercised using multiple RT fixtures.

## Test rules and verdicts

- Exercise actual Next route handlers and domain/database services. Mock-only authorization tests do not prove server-side access control.
- Use disposable local fixtures and independent database transactions/connections for concurrency tests. Do not mutate shared Neon financial data or production.
- For denied requests, assert both the HTTP/domain result and that protected rows, ledger rows, sessions, and audit rows did not change. Responses must not expose credentials, tokens, database details, internal IDs, or unrelated resident data.
- A test marked **Existing baseline test** is a source reference to rerun and review on the Launch Safety branch. It is not a claim that the Launch Safety branch has passed it.

Severity rules:

- **Critical:** unauthorized financial effect, cross-RT access, privilege escalation, broken financial idempotency/concurrency, or unauthorized privileged-account recovery. Any Critical result is a launch blocker.
- **High:** unauthorized sensitive data access, stale privileged access, working CSRF against a privileged or financial mutation, credential guessing without an effective limit, or broken session revocation. Any launch-relevant High result is a launch blocker.
- **Medium:** validation, rate-limit, or error-handling weakness that does not permit unauthorized access or financial mutation. Classify from the demonstrated effect.
- **Low:** safe, bounded behavior or usability-only failure with no security or data-integrity consequence.
