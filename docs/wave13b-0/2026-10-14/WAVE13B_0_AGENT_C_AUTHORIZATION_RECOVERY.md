### One-shot marker and replay boundary

`consumeAuthorizationOnce` creates `karturt-v1-staging-migration/consumed/<authorizationId>.used` under the Git common directory with exclusive file creation and file `fsync`. The marker is consumed after signature validation and typed confirmation, but before client creation. This prevents reuse within the same shared Git common directory and deliberately spends an authorization even if a later connection or migration fails.

The marker is local state, not a cross-host or cross-clone registry. Two separate clones or machines can each accept the same signed artifact because they do not share that Git common directory. The 64-hex shape also does not prove that IDs were generated uniquely. For future approval issuance, create each ID from at least 32 cryptographically random bytes, record it in an owner-controlled external issuance/spent ledger, and never distribute/copy a signed artifact to multiple execution hosts. If this limitation cannot be operationally controlled, D3 must wait for a separately reviewed replay-control design; do not describe the current marker as globally one-use.

## Timeout and unknown-outcome handling

The operator config sets PostgreSQL `statement_timeout` to 10 minutes, node-postgres `query_timeout` to 11 minutes, an outer JavaScript `Promise.race` deadline to 15 minutes, and a bounded client shutdown wait to 10 seconds. These are separate controls. The outer JavaScript deadline bounds the process-side wait; it does not cancel a query by itself. `PoolClient.release(error)` / `Pool.end()` bound local client cleanup but do not prove server-side cancellation or transaction rollback.

The exact-SHA disposable PostgreSQL 18.6 rehearsal (`38538027706`) used `pg.Pool` over loopback TCP, not Neon. Child processes exited naturally with codes 0/1/1 and no retry. In the 300 ms synthetic `SELECT pg_sleep(60)` scenario, the backend remained active at 3,046 ms after child exit and disappeared after 57,192 ms of observation without a cancellation request. This demonstrates why a local timeout or process exit is not an outcome proof. The operator does not use the Neon serverless/WebSocket driver, and that transport was not tested; do not transfer direct-TCP findings into a Neon cancellation or migration guarantee.

On timeout, process interruption, connection loss, migration error, shutdown error, or any uncertain response, treat the database outcome as unknown. Keep the authorization consumed; do not retry, re-run, edit the Drizzle ledger, compensate, reset, delete, or automatically rebuild. Stop and request a separately approved read-only reconciliation of the exact target's identity, migration ledger, and schema before considering any new authorization. A rollback or rebuild plan is a separate owner decision that must specify exact operations and preserve both the new project and the old staging project; production and the old staging target are never fallback targets.
